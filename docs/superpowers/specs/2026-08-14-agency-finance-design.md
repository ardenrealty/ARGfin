# Финансовое веб-приложение агентства недвижимости — дизайн

Дата: 2026-08-14
Статус: черновик на утверждение

## 1. Задача

Веб-приложение для одного пользователя (владелец агентства недвижимости, посуточная/долгосрочная аренда объектов). Ручной ввод сделок, платежей и расходов, автоматический расчёт прибыли и остатков по счетам.

**Ключевое требование:** прибыль и движение денег считаются раздельно. Стартовые вложения и личные изъятия не участвуют в прибыли, но участвуют в движении денег (остатке счёта).

## 2. Технологический стек

| Слой | Технология |
|---|---|
| Фронтенд | Next.js (App Router) + TypeScript + Tailwind CSS |
| Данные | Supabase (Postgres) |
| Авторизация | Supabase Auth, email + пароль, один аккаунт |
| Хостинг | Vercel |
| Графики | Recharts |

## 3. Безопасность

- Приложение полностью закрыто авторизацией. Никаких публичных страниц, кроме страницы входа. Next.js middleware проверяет сессию на всех маршрутах.
- **RLS включён на каждой таблице.** Политика: `user_id = auth.uid()` на select/insert/update/delete. CI/сборка должна падать (через миграционный lint-скрипт или тест), если на какой-то таблице RLS выключен.
- **Ключи.** В браузер уходит только `anon key`. `service_role key` — исключительно в серверных функциях (route handlers / server actions), хранится в `.env.local`, не коммитится (в `.gitignore`).
- **Soft delete.** Ни одна запись не удаляется физически. Поле `deleted_at`, все выборки и views фильтруют `deleted_at is null`.
- **Журнал изменений (`audit_log`):** таблица, куда пишется что изменено, когда, старое и новое значение (JSON diff), для каждой мутирующей операции на бизнес-таблицах. Правка задним числом обязана фиксировать оба значения дат (старое/новое).
- **Бэкап.** Кнопка «Выгрузить всё» — JSON со всеми таблицами пользователя. Плюс отдельный экспорт операций/отчётов в CSV.
- **Не хранить:** паспортные данные, полные номера карт. По клиенту — только имя и телефон.
- Сессия истекает через 7 дней, HTTPS обязателен (обеспечивается Vercel).

## 4. Модель данных

### Справочники

**accounts** — счета (несколько счетов с отдельными остатками: наличные, банк, эквайринг и т.п.)
`id, user_id, name, kind (bank | cash | card), is_active, created_at`

**objects** — объекты (квартиры/номера)
`id, user_id, title, address, type, owner_name, owner_contact, default_commission_pct, is_active, note`

**employees** — сотрудники
`id, user_id, name, role, payout_scheme (fixed | percent | mixed), base_salary, percent_rate, is_active`

**categories** — категории расходов
`id, user_id, name, group (ads | team | staff | personal)`
Стартовый набор группы `team`: еда, развлечения, транспорт, коворкинг, связь, софт.

### Основные таблицы

**deals** — сделки
`id, user_id, object_id, client_name, client_phone, booking_date, checkin_date, checkout_date, deal_amount, commission_pct, commission_amount, source (avito | cian | recommend | other), closed_by_employee_id, status (booked | prepaid | checked_in | completed | cancelled), note, created_at, updated_at, deleted_at`

`commission_pct` и `commission_amount` пересчитываются друг из друга от `deal_amount` — вводится любое из двух (реализуется в TS-слое формы, не в БД-триггере, чтобы избежать циклов округления).

**payments** — платежи по сделкам
`id, user_id, deal_id, kind (prepay | balance | full), amount, paid_at, recognized_at, account_id, note, deleted_at`
Одна сделка → от одного до нескольких платежей. `recognized_at` заполняется автоматически (см. §5), вручную не редактируется.

**transactions** — все прочие движения денег
`id, user_id, date, type, amount, account_id, account_to_id, category_id, employee_id, object_id, platform, period_start, period_end, is_general, note, created_at, deleted_at`

Значения `type`:

| type | Название | Знак | В прибыль |
|---|---|---|---|
| invest | Стартовое вложение | + | нет |
| other_income | Прочий доход | + | да |
| ads | Реклама и размещение | − | да |
| team | Общие траты команды | − | да |
| salary | Выплата сотруднику | − | да |
| staff_expense | Подотчётная трата | − | да |
| personal | Личная трата / изъятие | − | нет |
| transfer | Перевод между счетами | 0 | нет |

`platform`, `period_start`, `period_end`, `is_general`, `object_id` заполняются только при `type = ads`. `is_general = true` — реклама не привязана к конкретному объекту (не попадает в маржу объекта).
`account_to_id` заполняется только при `type = transfer`.

## 5. Правила расчёта

### Признание выручки

| kind платежа | recognized_at |
|---|---|
| full | = paid_at |
| prepay | = paid_at |
| balance | = deals.checkin_date |

Заполняется автоматически при сохранении платежа (БД-триггер или server action), вручную не редактируется.

### Отмена сделки

Предоплата невозвратная. При переводе сделки в `cancelled`:
- уже проведённые платежи остаются, признание не сторнируется;
- остаток к получению («ожидается») обнуляется для этой сделки;
- сделка не удаляется.

Возвраты в системе не предусмотрены.

### Ввод задним числом

- Все даты (`date`, `paid_at`, `booking_date`, `checkin_date`) редактируются вручную. Сегодняшняя дата — значение по умолчанию, не блокируется.
- Дата события (`date`/`paid_at`) и дата создания записи (`created_at`) — разные поля. Отчёты строятся по первому, аудит — по второму.
- **Никаких сохранённых остатков.** Остаток счёта, выручка периода, прибыль считаются запросом на лету (Postgres views/функции). Хранить накопительный баланс в таблице запрещено.
- **Ретроактивный пересчёт.** После добавления/правки операции все отчёты за затронутый период сразу показывают новые цифры — это следует автоматически из того, что отчёты не кэшируются.
- Редактирование и удаление доступны для любой записи независимо от возраста. Удаление — только мягкое (`deleted_at`).
- Предупреждение, а не запрет: если дата операции старше 60 дней или в будущем — пометка в форме («Дата в прошлом месяце», «Дата в будущем»), сохранение разрешено.
- Изменение `checkin_date` у сделки пересчитывает `recognized_at` у связанного платежа с `kind = 'balance'`.
- Правка задним числом пишется в `audit_log` с обоими значениями дат.

### Формулы (реализуются как Postgres views/функции)

```
Остаток счёта   = Σ payments(account) + Σ transactions(in) − Σ transactions(out) ± переводы

Выручка периода = Σ payments.amount, где recognized_at в периоде
                  + Σ transactions(other_income)

Расходы периода = Σ transactions(ads + team + salary + staff_expense)

Прибыль         = Выручка − Расходы

Ожидается       = Σ (deals.commission_amount − Σ payments по сделке)
                  по сделкам в статусе booked / prepaid / checked_in

Получено, но не признано = Σ payments, где paid_at ≤ сегодня < recognized_at

Внесено капитала = Σ transactions(invest)
Изъято лично     = Σ transactions(personal)

Свободные деньги = Капитал + Выручка − Расходы − Изъятия

Маржа по объекту = Σ признанных комиссий по объекту − Σ ads с этим object_id
```

`invest` и `personal` не входят в прибыль — гарантируется структурой view (эти типы просто не включены в SQL-выражение прибыли) и проверяется тестами (§8).

## 6. Экраны

**Дашборд**
- Карточки: остаток по счетам, выручка месяца, расходы месяца, прибыль месяца, ожидается остаток, получено но не признано, изъято лично.
- Столбчатый график выручка / расходы / прибыль по месяцам (Recharts).
- Горизонтальная полоса распределения денег: реклама, ФОТ, команда, подотчёт, личное, остаток.
- Список ближайших заселений с суммой ожидаемой доплаты.

**Сделки**
- Таблица с фильтрами: период, объект, статус, источник, сотрудник.
- Карточка сделки: параметры + список платежей + кнопка «Добавить платёж».
- Индикатор: оплачено / осталось.

**Операции**
- Единый журнал `transactions` с фильтрами по типу, счёту, категории, периоду.
- Быстрое добавление: сначала выбор типа, затем контекстная форма (набор полей меняется от типа).

**Справочники** — объекты, сотрудники, счета, категории.

**Отчёты**
- P&L за период: выручка → реклама → ФОТ → команда → подотчёт → прибыль.
- Остатки и обороты по счетам.
- Маржа по объектам: комиссии, реклама, разница.
- Сводка по сотрудникам: выплачено, подотчёт, итого.
- Эффективность площадок: сделок, комиссий, затрат на рекламу, стоимость сделки.
- Экспорт любого отчёта в CSV.

**Настройки** — бэкап, экспорт, смена пароля.

## 7. Порядок реализации

1. **Каркас** — схема БД, RLS, авторизация, справочники, CRUD операций, остатки по счетам.
2. **Сделки и платежи** — сделки, платежи, автоматическое признание, статусы, дебиторка.
3. **Отчёты** — P&L, маржа по объектам, площадки, сотрудники, экспорт CSV.
4. **Дашборд** — карточки, графики, полоса распределения, ближайшие заселения.
5. **Надёжность** — audit log, бэкап в JSON, мобильная вёрстка, тесты формул.

## 8. Обязательные тесты (pgTAP против views, с фикстурами)

1. Стартовое вложение не увеличивает прибыль, но увеличивает остаток счёта.
2. Личная трата не уменьшает прибыль, но уменьшает остаток счёта.
3. Предоплата в январе + заселение в феврале → выручка делится между двумя месяцами.
4. Полная оплата одним платежом → вся комиссия признана в дату платежа.
5. Отмена сделки после предоплаты → предоплата остаётся в выручке, остаток исчезает из «ожидается».
6. Перевод между счетами не меняет ни прибыль, ни суммарный остаток.
7. Реклама с `is_general = true` не попадает в маржу конкретного объекта.
8. Операция, внесённая сегодня с датой позапрошлого месяца, попадает в отчёт того месяца, а не текущего.
9. Правка суммы у старой операции меняет остаток счёта и прибыль за тот период, а не за сегодняшний.
10. Изменение даты заселения переносит признание остатка в другой месяц.

Плюс Vitest unit-тесты для TS-хелперов, не живущих в БД (пересчёт `commission_pct` ⇄ `commission_amount`, форматирование, клиентская валидация дат "давности").

## Технические решения

- **Формулы/агрегаты:** реализованы как Postgres views/функции, а не расчёт в TypeScript — гарантирует отсутствие сохранённых балансов и автоматический ретро-пересчёт при правках задним числом.
- **Тестирование формул:** pgTAP-тесты в БД с фикстурами, покрывающие все 10 сценариев §8.
